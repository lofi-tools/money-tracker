# EVM wallet inventory and acquisition evidence

The exports are actually under `.cache/airtable_export/`. Structural inspection found 108 records in `products-model2-draft.csv` and 124 in `wallets-Default view.csv`. The product catalogue includes MetaMask Ethereum, Polygon, BNB Chain, Arbitrum and zkSync labels, plus `wallet.zksync.io`. The wallet view includes BNB and USDT on BNB Chain, USDT/MATIC on Polygon, and mainnet ETH labels. Neither file contains an EVM wallet address or contract address.

These labels establish connector candidates, not authoritative holdings, chain-specific token mappings or proof that zkSync labels mean Era rather than Lite. No researched rates, old wallet balances or product catalogue rows were imported as live ledger positions. The user subsequently supplied a public address and explicitly requested database storage rather than hardcoding. It was registered as five account identities in the existing local portfolio DB; the address is intentionally omitted here.

The [EVM contract and setup guide](../spec/evm-wallets.md) documents implemented mappings, replay and reconciliation. Live Ethereum probing found 78 historical transaction hashes and 16 candidate token contracts for the supplied wallet. One public RPC returned a null historical transaction; another served history but encountered missing token metadata and later rate limiting. Missing metadata is now retained as unresolved contract coverage, with full reconciliation withheld. Request pacing and bounded throttle recovery are implemented. With pacing, a complete Ethereum acquisition was subsequently saved: 78 transactions, 14 resolved token contracts and two unresolved decimal mappings. Two pre-Byzantium receipt outcomes were obtained explicitly from Blockscout and retained for replay. Live ledger reconciliation matched Ethereum native balance and all 14 resolved token quantities exactly; full coverage remains withheld for the two unresolved contracts. zkSync Era had no discovered activity and an independently observed zero native balance, which reconciled. Polygon and Arbitrum address endpoints returned HTTP 403 challenge pages, so no history import was fabricated. BNB stopped at the missing `ETHERSCAN_API_KEY` requirement. Thus the five-chain connector foundation is implemented, but live five-chain coverage is not complete.

BNB discovery uses Etherscan V2 with an appropriate key/chain access unless a compatible Blockscout endpoint is supplied. Complete-capture caching exists; partial-page resume, robust reorg replacement, special tokens and protocol interpretation remain outstanding. Source selection is replaceable so individual service limitations do not become wallet identities or asset definitions.

Subsequent investigation identified the two contracts and recovered INS Promo’s historical scale; strict reconciliation now exposes its destroyed-contract balance gap. API-key access and the Polygon archive RPC have been tested. See [the current resolution findings](evm-contract-resolution.md) for the updated evidence and remaining blockers.
